# maplibre-gl v6 (6.7.0) migration audit — silent behavior changes

Codebase context: pinned `maplibre-gl` **6.7.0** (bundled `@maplibre/maplibre-gl-style-spec` **^26.4.1**, verified in [v6.7.0 package.json](https://github.com/maplibre/maplibre-gl-js/blob/v6.7.0/package.json)), recently upgraded from v2/v3-era patterns. Two bugs already proven in this codebase: (1) mixed legacy+expression filters compile as pure expressions; (2) `addImage` duplicate error on theme swap.

Sources: official [maplibre-gl-js CHANGELOG](https://github.com/maplibre/maplibre-gl-js/blob/main/CHANGELOG.md), [v5→v6 migration guide](https://maplibre.org/maplibre-gl-js/docs/guides/v5-to-v6-migration-guide/), [style-spec CHANGELOG](https://github.com/maplibre/maplibre-style-spec/blob/main/CHANGELOG.md), and the tagged v6.7.0 / style-spec main source itself. Every claim links its source. Versions are the gl-js version unless a `style-spec` version is named.

Legend: **CONFIRMED-BREAKING** = verified in changelog and/or v6.7.0 source. **PRE-EXISTING** = behavior exists since v2/mapbox era, not introduced by v6, but newly *reachable* or newly *diagnosed* because of a v6 change. **UNCERTAIN** = plausible but not confirmed from official sources.

---

## 1. setFilter / layer filters (KNOWN BUG #1 — mechanism confirmed)

**CONFIRMED-BREAKING — mixed legacy+expression filters now compile as a pure expression (legacy conversion skipped), so `["==", "$type", "LineString"]` evaluates a string literal and is always false.**

- What changed, in three steps:
  1. gl-js **6.0.0** (style-spec **25**): "Update maplibre-gl-style-spec to version 25, which now throws an error with warning severity instead of silently failing on encountering legacy expressions" — [CHANGELOG 6.0.0, issue #7792](https://github.com/maplibre/maplibre-gl-js/issues/7792). style-spec 25.0.0: "Change legacy filter expression validation to add suggestions on invalid expressions" — [style-spec CHANGELOG, PR #1709](https://github.com/maplibre/maplibre-style-spec/pull/1709).
  2. **6.0.0 final**: "Log style validation warnings instead of treating them as errors, so that a filter mixing legacy and expression syntax no longer aborts the style load and blanks the map" — [CHANGELOG 6.0.0](https://github.com/maplibre/maplibre-gl-js/blob/main/CHANGELOG.md) (cites PR [#7941](https://github.com/maplibre/maplibre-style-spec/pull/7941)). So in 6.0.0 pre-releases this was a hard abort (blank map); since 6.0.0 final it is a console warning and the map renders — with the filter silently wrong.
  3. style-spec **26.0.0**: "Add a `severity` field to `ValidationError` and improve legacy filter recognition" — [style-spec CHANGELOG, #1752](https://github.com/maplibre/maplibre-style-spec/issues/1752); rationale issue [#1751](https://github.com/maplibre/maplibre-style-spec/issues/1751).
- Source mechanism (verified in code):
  - Classification: one expression-only child "settles it for the whole tree" → mixed tree is classified `expression`; `isExpressionFilter` returns true; legacy `convertFilter` is skipped — [feature_filter/index.ts (`classifyFilter`/`classifyChildren`, `isExpressionFilter`)](https://github.com/maplibre/maplibre-style-spec/blob/main/src/feature_filter/index.ts).
  - Warning text `Mixing deprecated filter syntax with expression syntax is not supported…` comes from `getMixedFilterMessage` in the same file; it is emitted with `severity: 'warning'` by [`validateNoMixedLegacyFilter`](https://github.com/maplibre/maplibre-style-spec/blob/main/src/validate/validate_filter.ts).
  - gl-js 6.7.0 `emitValidationErrors`: `severity === 'warning'` → `warnOnce(...)` only, setter proceeds — [validate_style.ts L84](https://github.com/maplibre/maplibre-gl-js/blob/v6.7.0/src/style/validate_style.ts). `setFilter` validates through the same gate ([style.ts L1302](https://github.com/maplibre/maplibre-gl-js/blob/v6.7.0/src/style/style.ts)); a warning-severity finding does NOT block the set — the filter is compiled as an expression.
- Contrast with old majors (why this is new): gl-js **v2.0.0** (bundled spec) and style-spec **v24** (gl-js v5 line) used a heuristic where `any`/`all` with ANY legacy child → whole tree classified legacy → `convertFilter` attempted on the tree — [v2.0.0 feature_filter source](https://github.com/maplibre/maplibre-gl-js/blob/v2.0.0/src/style-spec/feature_filter/index.ts), [style-spec v24.0.0 feature_filter](https://github.com/maplibre/maplibre-style-spec/blob/v24.0.0/src/feature_filter/index.ts). The flip is style-spec 25 / gl-js 6.
- Guidance for v6.7.0: never mix syntaxes in one filter tree. Convert legacy tokens fully: `$type` → `["geometry-type"]`, `$id` → `["id"]` (the warning message itself suggests the exact replacement, see [test asserting `Replace ["!=","$type","LineString"] with ["!=",["geometry-type"],"LineString"]`](https://github.com/maplibre/maplibre-style-spec/blob/main/src/feature_filter/feature_filter.test.ts)). Sweep all `setFilter` calls and any static style JSON. **Note the same compile path is used for `queryRenderedFeatures`/`querySourceFeatures` filter options** (validated at [style.ts L1589/L1664](https://github.com/maplibre/maplibre-gl-js/blob/v6.7.0/src/style/style.ts)) — a mixed filter passed to a query is silently wrong there too.
- Related footnotes: `feature-state` expressions are not allowed in filters (mapbox-era rule, [style-spec CHANGELOG, mapbox #7366](https://github.com/maplibre/maplibre-style-spec/issues/1279) section); legacy `in` filters with scalar property key are still classified legacy so they keep working ([classifyFilter comments](https://github.com/maplibre/maplibre-style-spec/blob/main/src/feature_filter/index.ts)). `has` filter now returns false when the property exists but is `undefined` (style-spec 25.0.1, [#1712](https://github.com/maplibre/maplibre-style-spec/pull/1712)).

## 2. addImage / updateImage / hasImage / styleimagemissing (KNOWN BUG #2 + related)

**PRE-EXISTING but newly reachable — `Map#addImage` on an existing id fires an `error` event and does nothing: `An image named "flow-arrow" already exists.`**

- Source (v6.7.0): [`Style#addImage` — if `getImage(id)` exists, fire ErrorEvent and return](https://github.com/maplibre/maplibre-gl-js/blob/v6.7.0/src/style/style.ts) (L959). **Verified identical in v2.0.0, v3.0.0, v4.0.0, v5.0.0** (`style.ts` per tag) — this is mapbox-era behavior, NOT new in v6. Docs pattern: `if (!map.hasImage('cat')) map.addImage('cat', ...)` — [map.ts L3148](https://github.com/maplibre/maplibre-gl-js/blob/v6.7.0/src/ui/map.ts); [`hasImage` L3330](https://github.com/maplibre/maplibre-gl-js/blob/v6.7.0/src/ui/map.ts).
- Why the codebase hits it only now — **CONFIRMED-BREAKING in v6.0.0**: "`styleimagemissing` is now a notify-only event instead of the previous callback that allowed to provide an image… Use `Map.setMissingStyleImageResolver`" — [CHANGELOG 6.0.0, #7892](https://github.com/maplibre/maplibre-gl-js/issues/7892). In v5-and-earlier, calling `addImage` from a `styleimagemissing` listener silently resolved the pending request; v6 discards that. The migration guide shows the exact diff — [v5→v6 guide](https://github.com/maplibre/maplibre-gl-js/blob/main/docs/guides/v5-to-v6-migration-guide.md). If theme-swap code registers images both in `styleimagemissing`/`style.load` handlers, the second `addImage` now errors instead of silently winning.
- `updateImage` is the replace path ([`Map#updateImage` L3262](https://github.com/maplibre/maplibre-gl-js/blob/v6.7.0/src/ui/map.ts)); in 6.7.0 it throws on invalid argument types (L3276) and (per docs pattern) should be guarded with `hasImage`.
- v6.4.0: "Prevent a rejected missing style image resolver from blocking successfully resolved images in the same batch" ([#8146](https://github.com/maplibre/maplibre-gl-js/pull/8146/)) — resolver errors are batch-scoped.
- Guidance: on theme swap, either guard every `addImage` with `hasImage` (then `updateImage` when content changes), or `removeImage` + `addImage`, or move lazy image creation to `setMissingStyleImageResolver`. Listen to `error` during development — image add failures are error *events*, not exceptions.
- Unrelated but image-adjacent: `ImageSource.updateImage` accepts decoded images directly since 6.5.0 ([#7944](https://github.com/maplibre/maplibre-gl-js/pull/7944)) and sources can start without a URL in 6.7.0 ([#8167](https://github.com/maplibre/maplibre-gl-js/pull/8167)).

## 3. setFeatureState / getFeatureState / removeFeatureState

- **Signatures unchanged in v6.7.0**: `setFeatureState(feature: FeatureIdentifier, state)`, `removeFeatureState(target, key?)`, `getFeatureState(feature)` — [map.ts L3902/L3953](https://github.com/maplibre/maplibre-gl-js/blob/v6.7.0/src/ui/map.ts). No breaking changelog entry found for these APIs in v4/v5/v6.
- **CONFIRMED behavior fix (changes results)**: 6.0.0 — "Fix feature state bulk remove + feature set per-id set does not remove state of first feature" ([#7554](https://github.com/maplibre/maplibre-gl-js/pull/7554)). If code relies on the old buggy bulk-remove semantics, output changes. Feature-state storage was also internally rewritten in 6.0.0 ([#7550](https://github.com/maplibre/maplibre-gl-js/pull/7550), 3.4x speedup) and 6.0.0 fixed zoom lag with many state keys ([#7590](https://github.com/maplibre/maplibre-gl-js/pull/7590)).
- Related: 5.0.0 changed cluster id behavior with `promoteId` (promoted id used on non-clustered features) ([#4899](https://github.com/maplibre/maplibre-gl-js/pull/4899)) — affects `setFeatureState` addressing on clustered geojson sources.
- Guidance: after style swap, feature state lives with the source; a `setStyle` to a new theme with a *new source id* silently loses all feature state — re-apply states in the `style.load`/`styledata` handler.

## 4. queryRenderedFeatures

- **Argument shapes unchanged** (geometry-or-point + options). No changelog entry changes the signature.
- **CONFIRMED-BREAKING (results change) — v6.0.0**: "`zoomLevelsToOverscale` default value was changed to 4 … might have a side effect of changing a bit the results of `queryRenderedFeatures` and some rendering of polygon center label. To revert, set the value to `undefined`" ([#7537](https://github.com/maplibre/maplibre-gl-js/issues/7537)); repeated in the [migration guide](https://github.com/maplibre/maplibre-gl-js/blob/main/docs/guides/v5-to-v6-migration-guide.md).
- **CONFIRMED-BREAKING (results change) — v6.0.0**: GeoJSON nested object properties are now preserved as real objects instead of JSON strings; `JSON.parse` on them now throws `SyntaxError` ([#6992](https://github.com/maplibre/maplibre-gl-js/pull/6992), [migration guide section](https://github.com/maplibre/maplibre-gl-js/blob/main/docs/guides/v5-to-v6-migration-guide.md)). Hits feature click/hover handlers that parse properties.
- The mixed-filter compile issue (area 1) applies to the `filter` option of queries — same silent wrong results.
- Fixes altering edge behavior: 6.0.0 conflicting tile reloads erroring in `queryRenderedFeatures` ([#7765](https://github.com/maplibre/maplibre-gl-js/pull/7765)); 6.6.0 "Out of bounds" race ([#8064](https://github.com/maplibre/maplibre-gl-js/issues/8064)).

## 5. setPaintProperty / interpolate / zoom placement

- **CONFIRMED (rule) / UNCERTAIN (v6-specificity) — zoom must be the input of a TOP-LEVEL `step`/`interpolate`.** Verified in style-spec source: `findZoomCurve` accepts a zoom curve only at top level, allowing wrapping in `let`/`coalesce` only; otherwise error `'"zoom" expression may only be used as input to a top-level "step" or "interpolate" expression.'` — [expression/index.ts L527/L719-L751](https://github.com/maplibre/maplibre-style-spec/blob/main/src/expression/index.ts). A zoom nested inside `case`/`match` (e.g. `["case", hover, ["interpolate",["linear"],["zoom"],…], …]`) is a parse **error**.
- **NOT new in v6**: the rule dates to the original expressions rollout — style-spec CHANGELOG (10.x era): "Validate that zoom expressions only appear at the top level of an expression" ([mapbox-gl-js #5609](https://github.com/mapbox/maplibre-gl-js/issues/5609) as cited in [style-spec CHANGELOG](https://github.com/maplibre/maplibre-style-spec/blob/main/CHANGELOG.md)).
- What **is** new in v6 is how enforcement surfaces: in 6.0.0 the severity split (area 1) means *error*-severity findings (which this is) still abort a style load — a nested-zoom paint expression in the initial style JSON blanks the map ([validate_style.ts](https://github.com/maplibre/maplibre-gl-js/blob/v6.7.0/src/style/validate_style.ts): errors fire `ErrorEvent` and the caller "gives up on the style"); via `setPaintProperty` the value is rejected and the previous value stays, with an error event. 6.0.0 also improved messages to point at the offending property: "Improve runtime error warnings to point at the offending style location (e.g. `layers[3].paint.line-color`, `layers[3].filter`)" ([#7869](https://github.com/maplibre/maplibre-gl-js/pull/7869)).
- If nested-zoom-in-case "worked" before the upgrade, it most likely ran through legacy stop-function syntax that was migrated/leniently handled — **UNCERTAIN**; treat as: rewrite to `["interpolate", ["linear"], ["zoom"], z0, ["case", …], z1, ["case", …]]` (zoom curve at top, `case` in the outputs), which is the supported shape.
- Property typing note — **CONFIRMED type-level break, v6.0.0**: "`Improve types for {get,set}LayoutProperty, {get,set}PaintProperty` to be the actual type instead of `string`/`any`" ([#7481](https://github.com/maplibre/maplibre-gl-js/pull/7481)) — TS-only, but will surface as compile errors during the upgrade.
- Other paint-adjacent 6.x visual changes: icon-offset scaling disabled (6.0.0, [#7742](https://github.com/maplibre/maplibre-gl-js/issues/7742)); `line-opacity` overlap artifacts reworked into new `line-layer-opacity`/`fill-layer-opacity` properties (6.0.0 [#7490](https://github.com/maplibre/maplibre-gl-js/pull/7490)/[#7570](https://github.com/maplibre/maplibre-gl-js/pull/7570)); `line-dasharray` step with data-driven branches lagged one zoom (fixed 6.0.0 [#7705](https://github.com/maplibre/maplibre-gl-js/pull/7705)); light position now interpolated spherically (6.0.0 [#7919](https://github.com/maplibre/maplibre-gl-js/pull/7919)).

## 6. Events (error events, styledata/sourcedata timing)

- **CONFIRMED-BREAKING — v6.0.0**: "All map events are now real classes…" — `MapDataEvent` removed; `data`/`dataloading`/`dataabort` are now `MapSourceDataEvent | MapStyleDataEvent` (source events carry `sourceId`, `tile`, `sourceDataType`); `style.load` formalized as `MapStyleLoadEvent`; `on()`/`once()`/`off()` strongly typed ([#7789](https://github.com/maplibre/maplibre-gl-js/pull/7789)). Migration guide: "it is advised not to use `instanceof` but instead check the `type` field" — [guide](https://github.com/maplibre/maplibre-gl-js/blob/main/docs/guides/v5-to-v6-migration-guide.md). `styledata`/`sourcedata` event names and ordering are unchanged (verified in [events.ts](https://github.com/maplibre/maplibre-gl-js/blob/v6.7.0/src/ui/events.ts): styledataloading → styledata; sourcedataloading → sourcedata/…abort).
- WebGL failure path changed twice: 6.0.0 made no-WebGL2 observable via `error` event ([#7453](https://github.com/maplibre/maplibre-gl-js/pull/7453)); **6.7.0 (pinned version) throws `GPUInitializationError` from the constructor instead** ([#8066](https://github.com/maplibre/maplibre-gl-js/issues/8066)) — a try/catch around `new Map()` is required, an `error` listener alone will never see it.
- Error-event volume: 6.x fires more error events than v2-era code expects (addImage duplicates, addLayer duplicates, stricter validation) — apps that never registered `map.on('error')` historically now see console noise, and apps that *did* must not treat every error as fatal.
- Older majors (for the jump from v3): 5.0.0 changed `map.on(...)` to return a `Subscription` (chaining `map.on('x').on('y')` silently stops working) ([#5080](https://github.com/maplibre/maplibre-gl-js/pull/5080)).

## 7. addLayer / addSource re-adding on style swap

- **PRE-EXISTING semantics, verified in v6.7.0 source**: `addLayer` with an existing id fires `error` event `"Layer "X" already exists on this map."` and no-ops ([style.ts L1102](https://github.com/maplibre/maplibre-gl-js/blob/v6.7.0/src/style/style.ts)); `addSource` with an existing id **throws** `"Source "X" already exists."` ([style.ts L1016](https://github.com/maplibre/maplibre-gl-js/blob/v6.7.0/src/style/style.ts)). Guard with `getLayer(id)`/`getSource(id)` before re-adding after a theme swap.
- **CONFIRMED stricter validation in v6.0.0**: `map.addSource` now validates `raster-dem` sources (previously skipped), and unknown source types no longer fail the whole style ([#7941](https://github.com/maplibre/maplibre-gl-js/pull/7941)). `setTerrain` argument is also validated now (6.0.0, same PR).
- `setStyle` diff behavior (object → diff by default; `transformStyle` option since 3.0.0 [#1632](https://github.com/maplibre/maplibre-gl-js/pull/1632)) is unchanged in v6; note images/layers added at runtime can survive a diffed `setStyle`, which is exactly how a theme swap produces "already exists" on `addImage` (area 2).
- `GeoJSONSource.setData` lost its second parameter (`waitForCompletion`) and return value in 6.0.0 ([#7538](https://github.com/maplibre/maplibre-gl-js/issues/7538)) — if code passed a callback as the 2nd arg it is silently dropped.

## 8. Other v6 items that can bite a v2/v3-era codebase

- **CONFIRMED-BREAKING — 6.0.0: ESM-only** distribution; UMD/`maplibre-gl.js` script tag and CJS `require()` gone; default import must become `import * as maplibregl` or named imports ([#6254](https://github.com/maplibre/maplibre-gl-js/pull/6254), [guide](https://github.com/maplibre/maplibre-gl-js/blob/main/docs/guides/v5-to-v6-migration-guide.md)). CJS consumers fail with `ERR_PACKAGE_PATH_NOT_EXPORTED`.
- **CONFIRMED-BREAKING — 6.0.0: WebGL2 required**; WebGL1 removed ([#7453](https://github.com/maplibre/maplibre-gl-js/pull/7453)).
- **CONFIRMED-BREAKING — 6.0.0: `map.transform` removed**; `Map` composes `Camera` ([#7800](https://github.com/maplibre/maplibre-gl-js/pull/7800)).
- **CONFIRMED-BREAKING — 6.0.0: `#pragma mapbox` → `#pragma maplibre`** in shaders ([#7761](https://github.com/maplibre/maplibre-gl-js/issues/7761)).
- **CONFIRMED-BREAKING — 6.0.0: TypeScript target ES2022**; older toolchains must transpile ([#7404](https://github.com/maplibre/maplibre-gl-js/pull/7404)).
- **CONFIRMED-BREAKING — 4.0.0: callbacks → Promises** — `map.loadImage(url, cb)` no longer invokes a callback (returns a Promise; a second-arg callback is ignored → images silently never added) ([#3233](https://github.com/maplibre/maplibre-gl-js/pull/3233), [#3422](https://github.com/maplibre/maplibre-gl-js/pull/3422)); cluster methods `getClusterExpansionZoom/Children/Leaves` return Promises ([#3421](https://github.com/maplibre/maplibre-gl-js/pull/3421)); `setRTLTextPlugin` ([#3418](https://github.com/maplibre/maplibre-gl-js/pull/3418)) and `addProtocol` ([#3433](https://github.com/maplibre/maplibre-gl-js/pull/3433)) promise-based; global `maplibregl.*` getters/setters removed ([#3601](https://github.com/maplibre/maplibre-gl-js/pull/3601)); attribution on by default, `customAttribution` option removed ([#3618](https://github.com/maplibre/maplibre-gl-js/pull/3618)).
- **CONFIRMED-BREAKING — 5.0.0: WebGL context options moved** to `canvasContextAttributes` (`antialias`, `preserveDrawingBuffer`, `failIfMajorPerformanceCaveat`) ([#5196](https://github.com/maplibre/maplibre-gl-js/pull/5196)).
- **CONFIRMED-BREAKING — 3.0.0**: terrain moved from `style.terrain` to `map.terrain` ([#1628](https://github.com/maplibre/maplibre-gl-js/pull/1628)); non-conforming `hsl()` colors rejected ([#2376](https://github.com/maplibre/maplibre-gl-js/pull/2376)); `mapboxgl-` CSS classes removed ([#1575](https://github.com/maplibre/maplibre-gl-js/pull/1575)); `LngLat.toBounds()` replaced by `LngLatBounds.fromLngLat()` ([#2188](https://github.com/maplibre/maplibre-gl-js/pull/2188)).
- 6.7.0 perf note: `{validate: false}` on style setters now also skips the whole-style error-context snapshot ([#8259](https://github.com/maplibre/maplibre-gl-js/issues/8259)) — a cheap way to cut addLayer cost during bulk theme setup, but it disables the warnings this audit relies on.

## 9. Explicitly checked, no v6 change found

- `queryRenderedFeatures` argument shapes (geometry | point + options) — unchanged.
- `setFeatureState`/`getFeatureState`/`removeFeatureState` signatures — unchanged (behavior fix in 6.0.0, area 3).
- `styledata`/`sourcedata` event names and load ordering — unchanged in v6 (event payload *types* changed, area 6).
- `hasImage` — still present and documented in 6.7.0.
- Legacy stop-function paint syntax (`{"stops": …}`) — still accepted by the spec (legacy expression support retained; only *mixed legacy+expression filters* and *legacy expression validation severity* changed).
