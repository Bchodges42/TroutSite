# Trout codebase guide

## Purpose and scope

This document is a maintainer-oriented guide to the Trout websites repository. It explains the
runtime architecture, package boundaries, data flow, offline behavior, build/deploy path, and the
files to reach for when making common changes.

It describes the architecture present on **2026-09-16**. Exact content counts are generated and
change independently of this guide. The current implementation includes the map-first PWA,
the API ingestion/evidence pipeline, the shop portal, the Astro marketing site, generated static
snapshots, and the consolidated Playwright QA suite.

The product is designed around two principles:

1. **Offline first:** a visitor can use bundled hatch content and previously fetched data without
   a network connection.
2. **Privacy by architecture:** there are no visitor accounts, no location upload, no server-side
   logbook, and no third-party read-path requests. The shop portal is a separate, token-authenticated
   publishing surface.

## 1. The shortest useful mental model

Trout is a static-data publishing system with a small dynamic write surface.

```text
packages/content YAML + source data
                 │
                 ├── validate → build compact content pack
                 │                       │
live sources ────┴── API jobs → SQLite ───┴── snapshot builder
                                      │
                         apps/web/public/v1 + /content
                                      │
       ┌──────────────────────────────┼──────────────────────────────┐
       │                              │                              │
   apps/web                       apps/marketing                  apps/admin
   React PWA                      Astro static SEO site             React shop portal
   same-origin read path          fixture or snapshot build          token-authenticated writes
       │                              │                              │
       └────────────── main API/static origin :8787 ─────────────────┘
                         plus secondary origins :8788 / :8789
```

There are three important kinds of data:

| Data | Source of truth | Published/consumed as | Freshness behavior |
|---|---|---|---|
| Hatch taxa, fly patterns, hatch charts, fishing information | YAML/JSON under `packages/content` | `/content/*.json` and `/v1/hatch/...` | Static between content builds; precached by the PWA |
| Streams, shops, conditions, stocking, reports, evidence | API SQLite database plus content pack | `/v1/*.json` snapshots | Regenerated by deploy/cron; cached in Dexie and Workbox |
| Personal settings, logbook, seen-state, shop drafts | Browser storage | Never published automatically | Local to the current browser |

The API is not a conventional JSON application for most reads. It generates contract-shaped JSON
files and serves them statically. The one notable dynamic catalog read is `GET /v1/streams`, which
reads `v1/streams.json` and applies the optional `?state=` filter. The one product write path is
the shop report portal.

## 2. Repository layout and package graph

The root is a pnpm workspace (`pnpm-workspace.yaml`) using Node >=20 and pnpm 9.15.9.

| Path | Role in the system |
|---|---|
| [`apps/web`](../apps/web) | React 18 + Vite PWA. Map-first home, hatch key, conditions, stocking, shop reports, logbook, settings, offline storage. |
| [`apps/api`](../apps/api) | Fastify server, SQLite database, migrations, ingestion adapters, evidence providers, scheduled jobs, snapshot builder, portal routes. |
| [`apps/admin`](../apps/admin) | React shop-report portal. Expiring HMAC token login, local drafts, report composer, published-report history. |
| [`apps/marketing`](../apps/marketing) | Astro static/programmatic SEO site. Uses bundled fixtures by default and generated snapshots when `MARKETING_DATA_DIR` is set. |
| [`packages/contracts`](../packages/contracts) | Shared Zod schemas, inferred TypeScript types, endpoint map, fishability scoring, hatch ranking, freshness helpers. This is the compatibility boundary. |
| [`packages/ui`](../packages/ui) | Shared design tokens and React primitives (`Button`, `Card`, `Chip`, `DataBadge`, `EmptyState`, `LastUpdatedChip`). |
| [`packages/content`](../packages/content) | Source YAML/JSON content catalog, validation, report, and compact pack generation. |
| [`e2e`](../e2e) | Canonical Playwright suite for marketing, web/PWA, portal, API fixtures, and fieldwork/map behavior. |
| [`infra`](../infra) | Deploy, PM2, static secondary-origin server, Cloudflare Tunnel template, backup and snapshot-sync operations. |
| [`docs`](.) | ADRs, data-source decisions, atlas audits, implementation handoffs, operational notes, and this guide. |

Root commands are recursive unless a filter is specified:

```text
pnpm dev                 Run workspace dev scripts in parallel
pnpm build               Build every workspace package
pnpm test                Run package-level Vitest suites
pnpm lint                Run package-level ESLint suites
pnpm validate:content    Validate the source catalog and cross-references
pnpm e2e                 Run the canonical Playwright suite
pnpm e2e:web             Run only the Playwright web project
```

The root `package.json` is intentionally thin. Most behavior lives in the package manifests and
their local scripts.

### Build-order dependency

The important build dependency is:

```text
contracts → ui/content → api/web/admin/marketing → e2e
```

In particular:

- `@trout/contracts` must be built before API scripts that import its runtime `dist` output.
- `@trout/content` must be built before `apps/admin` or API snapshot generation, because the portal
  imports `@trout/content/pack/*` and the snapshot builder reads `packages/content/dist/pack`.
- A full `pnpm -r build` normally establishes these relationships through workspace ordering.

## 3. Shared contracts: the system’s vocabulary

[`packages/contracts/src/index.ts`](../packages/contracts/src/index.ts) re-exports all public schemas
and pure functions. Consumers should use these exports instead of inventing local shapes.

### Main domain schemas

The schema files cover:

- `Stream`, `IdealFlow`, waterbody types, state IDs, regions, official sources.
- `GaugeReading`, `ConditionSnapshot`, and `ConditionScore`.
- `StockingEvent` and species/date precision.
- `BugTaxon`, `FlyPattern`, `BugObservation`, `HatchChart`, and hatch stages/time of day.
- `Shop`, `ShopReport`, and hot patterns.
- `WaterEvidence` and its observation, stocking, regulation, and error records.
- Provenance and fishing-information structures.

Zod parsing is used at boundaries rather than only for TypeScript compile-time confidence. The API
validates data before writing snapshots; the web validates payloads before putting them into Dexie;
marketing validates its build inputs; and tests validate fixtures.

### Frozen endpoint map

[`packages/contracts/src/endpoints.ts`](../packages/contracts/src/endpoints.ts) defines the canonical
read/write surface:

| Contract entry | URL | Shape/purpose |
|---|---|---|
| `streams` | `GET /v1/streams` | All `Stream` records; optional `?state=TN` filtering is applied by Fastify. |
| `conditionsLatest` | `GET /v1/conditions/latest.json` | `ConditionSnapshot[]` for monitored/catalog waters. |
| `stocking` | `GET /v1/stocking/{state}.json` | Full `StockingEvent[]` history for a state. |
| `stockingRecent` | `GET /v1/stocking/{state}-recent.json` | Three-month, newest-first slice; may include scheduled future rows. |
| `hatch` | `GET /v1/hatch/{region}/{month}.json` | One `HatchChart`. |
| `shops` | `GET /v1/shops/{state}.json` | `Shop[]`. |
| `reportsRecent` | `GET /v1/reports/recent.json` | Recent attributed `ShopReport[]`. |
| `evidenceWaters` | `GET /v1/evidence/waters.json` | Provenance-first `WaterEvidence[]`. |
| `portalReports` | `POST /v1/portal/reports` | The authenticated shop write route. |
| `healthz` | `GET /healthz` | Process, job, and conditions-feed health. |

`GET /v1/portal/me` is an additive portal route implemented by the admin/API seam but is deliberately
not added to the frozen endpoint map without an ADR. That distinction matters when changing contracts.

### Fishability scoring

[`scoreConditions`](../packages/contracts/src/scoreConditions.ts) is deterministic and has no clock,
network, or randomness. It receives a stream and readings and returns a value, reasons, and an
`assessed` flag.

The current model:

- Flow dominates. A reading inside any configured ideal CFS range starts at 80; out-of-range flow
  falls toward a floor of 10 based on relative distance.
- A stage-height-only reading starts at 50 and is called limited-confidence.
- Temperature adds 10 in the 6–20°C ideal window, does nothing in the marginal bands, subtracts 15
  below 2°C, and subtracts 30 above 24°C.
- Scores are clamped to 0–100.
- `assessed: false` means “there was not enough usable data”; it is not the same thing as a real
  score of 0/Poor.
- Readings are filtered to the stream’s configured gauge IDs before scoring.

This is intentionally a transparent rule system. It is not an AI prediction model.

### Hatch matching

[`matchHatch`](../packages/contracts/src/matchHatch.ts) ranks taxa from a bug observation,
region/month hatch charts, and the taxa catalog. The maximum raw score is 8:

- five possible observation-attribute points: size, tails, gills, body shape, body color;
- two points when the taxon appears in the matching region/month hatch chart;
- one point when the taxon’s regional season record includes the month.

Zero-score taxa are omitted. Ties break by score, common name, then ID, so the offline flow is
repeatable and testable.

## 4. Content catalog and pack pipeline

[`packages/content`](../packages/content) is the authoring system for domain knowledge. It is not a
database migration layer and it is not a UI-only fixture directory.

The current source tree contains approximately:

| Source collection | Current count in the checkout |
|---|---:|
| Bug/taxon YAML files | 103 |
| Fly-pattern YAML files | 155 |
| Stream/water YAML files | Derived from `packages/content/streams/tn` |
| Shop YAML files | 23 |
| Hatch region YAML files | 12 regions × 12 months |

The validator’s explicit floors are 100 taxa, 150 patterns, 60 streams, 15 shops, and at least one
hatch region. The compact pack budget is 20 MB. These are Definition-of-Done gates, not merely
documentation targets.

### Source layout

```text
packages/content/
├── bugs/                 Bug taxa, including illustration references
├── patterns/             Fly patterns and license/attribution metadata
├── hatch/tn/             One YAML file per region with all twelve months
├── streams/tn/           Water catalog entries and official sources
├── shops/tn/             Shop identities and report enablement
├── data/                 Fishing information, verified gauges, additional data
└── scripts/
    ├── lib.ts            YAML loading, schema parsing, reference checks
    ├── regions.ts        Launch-region registry
    ├── validate.ts       CI gate and coverage/floor reporting
    ├── build.ts          Compact JSON pack generation
    └── report.ts         Human-readable catalog report
```

### Validation behavior

[`scripts/lib.ts`](../packages/content/scripts/lib.ts) parses YAML through the contracts and checks:

- duplicate IDs;
- unknown regions, taxa, patterns, and hatch references;
- missing or malformed SVG illustrations;
- license/attribution consistency;
- stream official-source requirements;
- gauge ID format and membership in the verified-gauge fixture;
- advisory fishery/year-round consistency;
- geometry/provenance leakage into angler-facing stream notes;
- all twelve months for every registered hatch region.

`pnpm validate:content` runs [`scripts/validate.ts`](../packages/content/scripts/validate.ts). Warnings
are printed for documented gaps; schema/reference/floor failures exit non-zero.

### Pack output

[`scripts/build.ts`](../packages/content/scripts/build.ts) deletes and rebuilds `dist/pack` with:

```text
bugs.json                 { taxa: [...] } plus inlined SVG line art
patterns.json             { patterns: [...] }
streams.json              { streams: [...] }
shops.json                { shops: [...] }
regions.json              { regions: [...] }
fishing.json              { fishing: ... }
hatch/{region}/{month}.json
meta.json
```

The PWA ultimately consumes bare arrays at `/content/taxa.json` and `/content/patterns.json`; the
API snapshot builder strips pack-only extras and re-validates the public payloads before writing them.
The admin portal consumes the built `streams.json` and `patterns.json` directly for its composer.

## 5. The web PWA (`apps/web`)

### Bootstrap and providers

[`src/main.tsx`](../apps/web/src/main.tsx) installs the service worker immediately and composes:

```text
StrictMode
└── QueryClientProvider (TanStack Query, offlineFirst)
    └── ThemeProvider
        └── SettingsProvider
            └── MotionSettings
                └── BrowserRouter
                    └── App
```

The global query defaults are deliberately offline-first: one retry, no window-focus refetch, and
no spinner that blocks the initial cached render.

[`src/App.tsx`](../apps/web/src/App.tsx) makes `/` map-first. The main route groups are:

| Route | Component | Purpose |
|---|---|---|
| `/` | `MapPage` | Tennessee field atlas and water selection. |
| `/browse` | `BrowsePage` | Search/discovery list of waters. |
| `/hatch-key` | `HatchKeyPage` | Guided bug-observation flow and deterministic ranked taxa. |
| `/taxa/:taxonId` | `TaxonDetailPage` | Taxon details and imitating patterns. |
| `/patterns/:patternId` | `PatternDetailPage` | Fly-pattern detail. |
| `/charts`, `/charts/:regionId/:month` | Hatch chart pages | Region/month hatch timing. |
| `/conditions`, `/conditions/:streamId` | Conditions/stream detail | Current score, readings, freshness, and reasons. |
| `/stocking` | `StockingPage` | State stocking schedule and recent window. |
| `/shops` | `ShopsPage` | Shop directory and attributed reports. |
| `/logbook` | `LogbookPage` | Local fishing log. |
| `/settings` | `SettingsPage` | Units, default state, reduced motion, cache controls. |
| `/fishing-info`, `/regulations` | `FishingInfoPage` | Fishing information and regulations content. |
| `/about` | `AboutPrivacyPage` | Product/privacy disclosure. |

`AppShell` owns the shared navigation, responsive chrome, offline banner behavior, and outlet
layout. The map feature is intentionally isolated under `src/features/map` because it has its own
geometry, camera, label, flow-arrow, QA, and MapLibre concerns.

### Offline data flow

The client-side fetch path is in [`src/lib/snapshots.ts`](../apps/web/src/lib/snapshots.ts):

1. Resolve the endpoint, including fixture-mode URL rewriting when enabled.
2. If the browser is known offline, read the schema-validated record from Dexie immediately.
3. Otherwise fetch same-origin JSON with an 8-second timeout.
4. Parse the response with the supplied Zod schema.
5. Store the payload and its network `fetchedAt` timestamp in Dexie.
6. If the request fails or the payload is invalid, fall back to the last valid Dexie record.
7. Return `live: false` for cached/offline data so the UI can say “Offline · last known …”.

The IndexedDB database is defined in [`src/lib/db.ts`](../apps/web/src/lib/db.ts) as `trout-web`:

| Table | Contents | Privacy boundary |
|---|---|---|
| `snapshots` | URL-keyed schema-validated JSON plus `fetchedAt`/`expiresAt` | Local cache only |
| `logbook` | Stream/date/notes/flies entries | Never sent to the API |
| `settings` | Units, default state, reduced motion | Local preference |
| `seen` | Previous readings shown for a stream | Local “what changed” baseline |

Clearing cached snapshots does not delete the personal logbook or settings; it also clears seen-state
because that state is meaningful only alongside cached conditions.

### Service worker and cache policy

[`vite.shared.ts`](../apps/web/vite.shared.ts) defines the production and fixture PWA behavior:

- app shell, fonts, icons, SVG, and directly shipped atlas context are precached;
- content pack and hatch charts are precached when present because they are static between content
  deployments;
- hourly conditions, stocking, shops, reports, and evidence use runtime `NetworkFirst` caching;
- topology/terrain assets under `/atlas/topo/` use `CacheFirst` with a longer lifetime;
- HTTP responses under `/v1`, `/data`, and `/content` are marked `no-store` by the local serving
  layers so an HTTP cache cannot masquerade as a live reading;
- the service worker is not allowed to turn API/data misses into HTML shell responses.

This is a two-layer offline strategy: Workbox retains network responses and the app explicitly keeps
schema-validated copies in Dexie. The UI still reports whether the current value is live or cached.

### Fixture mode

`apps/web` has two useful build flavors:

- normal production build: expects the API/snapshot tree to be available at the frozen URLs;
- `build:fixtures`: copies `apps/web/fixtures/data` into `dist` at `/v1/...` and `/content/...` so
  `vite preview` behaves like a static production origin for deterministic QA.

`DEV_FIXTURES=1 vite dev` uses the Vite middleware in `vite.config.ts` to serve extensionless
snapshot paths as JSON. This avoids Vite treating paths such as `/v1/streams` as JavaScript modules.

### Map and atlas

The map feature is more than a single component:

| Area | Files | Responsibility |
|---|---|---|
| Map shell/camera | `MapPage.tsx`, `RiverMapPage.tsx`, `useMapState.ts` | Full-bleed layout, camera/history/deep-link state, responsive inspector. |
| Geometry/data | `useRiverMapData.ts`, `riverIndex.json`, `streams-geo.json` | Join catalog streams to shipped geometry and water metadata. |
| Rendering | `TennesseeMap.tsx`, `mapStyle.ts`, `mapTokens.ts` | MapLibre source/layer setup and theme-aware styles. |
| Discovery | `BrowsePage.tsx`, `RiverSearch.tsx`, selectors | Search, list cards, near-me sorting, selection. |
| Meaning | `labelPolicy.ts`, `fisheryType.ts`, `waterDecision.ts` | Label hierarchy, fishery grouping, condition/selection decisions. |
| Interaction chrome | `MapControls.tsx`, `MapLegend.tsx`, `MapModeControl.tsx`, `HatchMonthControl.tsx` | Controls, legend, hatch/month context. |
| QA | `qa/*`, `QaPanel.tsx` | Internal `?qa=1` geometry audit overlay and defect navigation. |
| Navigation detail | `RiverDrawer.tsx`, `RiverInspector.tsx` | Selected-water summary, scores, evidence, sources, and actions. |

The large map assets live under `apps/web/public/atlas`: rivers/lakes/roads, boundaries, places,
provenance, contours, and hillshade tiles. The build scripts under `apps/web/scripts` fetch and
assemble TIGER/NHD/Census-derived material, perform continuity/deduplication/geometry gates, and
generate orientation and context assets. Treat `docs/GEO-AUDIT.md`, `docs/CONTINUITY-AUDIT.md`,
`docs/atlas-sources.md`, and `docs/flow-orientation.md` as part of the atlas contract before
editing generated geometry.

The map is Tennessee-centered in the current tree. `src/lib/endpoints.ts` exposes
`V1_STATES = ['TN']`; this is a stronger indicator of current launch scope than the older root
README language mentioning TX/OK/AR.

## 6. The API and publishing pipeline (`apps/api`)

### Fastify read path

[`src/server.ts`](../apps/api/src/server.ts) loads environment settings, opens SQLite, builds the
Fastify app, and listens on the configured host/port. [`src/app.ts`](../apps/api/src/app.ts) wires:

- `GET /healthz`;
- `GET /v1/streams`, including contract parsing and `?state=` filtering;
- portal routes when a database is present;
- CORS only for allow-listed portal origins;
- `/v1` static snapshots from `apps/web/public/v1`;
- `/content` static pack files from `apps/web/public/content`;
- the built PWA from `apps/web/dist`;
- SPA fallback for navigation paths while keeping API/data misses as real 404s.

The server redacts authorization headers, cookies, and remote address/port from logs. The body limit
for portal writes is 128 KiB.

The static-prefix separation is intentional. Two root static mounts caused a route collision during
integration; ADR 0006 records why `/v1` and `/content` are separate mounts.

### SQLite and migrations

[`src/db.ts`](../apps/api/src/db.ts) opens `better-sqlite3`, enables WAL/busy timeout behavior, and
applies every ordered SQL file under `apps/api/migrations`. The migration history currently covers:

```text
001_init.sql                         Core streams, gauges, shops, reports, jobs
002_gauge_readings_normalized.sql    Normalized gauge observations
003_report_photo_url.sql             Additive shop-report photo URL support
004_stream_species.sql               Stream species data
005_stocking_date_precision.sql      Scheduled/date-precision semantics
006_streams_waterbody_types.sql      River/creek/lake/tailrace/etc. classification
007_evidence_runs.sql                Provenance/evidence job storage
```

The production database is normally `apps/api/data/trout.db` and is gitignored. Raw source captures
are kept under the configured raw-data directory rather than embedded in published JSON.

### Snapshot generation

[`src/snapshots/build.ts`](../apps/api/src/snapshots/build.ts) is the bridge between the database,
the content pack, and the public read path. It:

1. reads the stream catalog from SQLite and writes `apps/web/public/v1/streams.json`;
2. selects latest gauge readings and computes a `ConditionSnapshot` per stream with the shared
   `scoreConditions` function;
3. writes full and recent stocking files per state;
4. writes shops per state;
5. writes recent reports (the current query window is the last 30 days, newest first);
6. re-emits the latest evidence run as `/v1/evidence/waters.json`;
7. reads the built content pack and writes `/content/taxa.json`, `/content/patterns.json`,
   `/content/fishing.json`, and `/v1/hatch/{region}/{month}.json`;
8. schema-validates payloads before atomic writes;
9. prunes state/hatch files that no longer correspond to current data.

Conditions use `nextExpectedUpdate`: one hour in the future when the gauges job is healthy, and
immediately stale when the last gauge job failed. This prevents a valid-looking but stale feed from
being presented as current.

### Ingestion and evidence jobs

[`src/pipeline.ts`](../apps/api/src/pipeline.ts) centralizes the four job names:

| Job | Primary responsibilities |
|---|---|
| `gauges` | USGS instantaneous values plus condition readings bridged from TVA/USACE where configured. |
| `stocking` | State adapters; Tennessee is implemented in `src/ingest/stocking/tn.ts`. |
| `evidence` | Assemble provenance-first water evidence from USGS, TVA, USACE, and TWRA-related sources. |
| `snapshots` | Regenerate the public static tree from database/content state. |

The cron worker in [`src/cron.ts`](../apps/api/src/cron.ts) schedules:

```text
gauges    hourly at :05
stocking  daily at 06:00
evidence  daily at 06:20
snapshots nightly at 04:30, plus deploy-time/manual runs
```

Only one job is allowed to run at a time in the cron process. Every run is recorded in `jobs_log` by
[`src/jobs/run.ts`](../apps/api/src/jobs/run.ts), and `/healthz` reports the latest status/detail
per job. A failed job is soft-failed so the worker survives; the snapshot/health logic marks the
published feed stale or unhealthy instead of silently pretending it is current.

`pipeline.ts --dry-run` is an especially useful maintenance seam: it parses recorded fixtures for
USGS, stocking adapters, and evidence providers without touching the database, snapshots, raw files,
or network.

### Public health is feed health

`/healthz` is not only a process liveness probe. When wired with the database and public snapshot
directory, it also evaluates whether the conditions feed has healthy coverage/freshness. The deploy
script refuses to finish if the conditions feed is structurally present but catalog-wide coverage is
unhealthy.

## 7. The shop portal (`apps/admin`)

The portal is a small, separate React application with no account system. It uses a signed token:

```text
v1.<shopId>.<issuedAtMs>.<expiresAtMs>.<signature>
```

Token creation/verification is shared conceptually between:

- [`apps/admin/src/lib/tokenNode.ts`](../apps/admin/src/lib/tokenNode.ts) and
  `scripts/mint-token.ts` for operator-side minting;
- [`apps/api/src/portal/tokens.ts`](../apps/api/src/portal/tokens.ts) for server verification;
- [`apps/admin/src/lib/tokenFormat.ts`](../apps/admin/src/lib/tokenFormat.ts) for browser parsing and
  expiry sanity checks.

The browser stores the token in localStorage only after the API accepts it. It sends the token in an
`Authorization` header; there are no cookies or passwords.

### Portal flow

```text
boot → inspect stored token → GET /v1/portal/me
     ├── invalid/expired → login textarea
     └── valid → PortalView
                    ├── ComposerView → local draft or POST /v1/portal/reports
                    └── HistoryView → local drafts + public recent-report snapshot filtered by shop
```

The composer validates dates, body length, hot-pattern rows, hook sizes, and optional HTTPS photo
URLs. Drafts are stored in `localStorage` under `trout.admin.drafts.v1`. The public report snapshot
is read-only in the portal; publishing is the only write.

In development, `main.tsx` starts an MSW browser worker unless `VITE_ENABLE_MSW=false`. This keeps
the portal clickable before a real API is available. The canonical e2e suite disables that shortcut
and drives the real API instance.

The portal’s `GET /v1/portal/me` endpoint and the additive `photoUrl` input are documented by the
implementation, contract tests, and relevant ADRs. Do not assume that every portal-only shape is
part of the frozen public contracts package.

## 8. The marketing site (`apps/marketing`)

`apps/marketing` is an Astro static site. It is build-time data driven rather than a live API client.

[`src/data/load.ts`](../apps/marketing/src/data/load.ts) selects its inputs as follows:

- with `MARKETING_DATA_DIR`, read generated files from the web public tree;
- otherwise, read the checked-in fixture JSON under `src/data/fixtures`.

It parses taxa, patterns, hatch charts, streams, stocking, shops, and reports with the shared Zod
schemas, performs cross-reference checks, and derives condition snapshots from fixture readings when
needed. This makes local/CI marketing builds deterministic while allowing deploy to render from the
latest generated snapshot tree.

### Page families

The current routes include:

- home, install, about, privacy, and the blog;
- state fishing and regulations pages;
- state stocking pages;
- state stream index and stream detail pages;
- state/region hatch pages;
- a “when does [state] stock trout” programmatic page;
- generated `robots.txt` and `sitemap.xml`.

`Base.astro`, `src/lib/seo.ts`, and the reusable components (`HatchChartTable`, `StockingTable`,
`ConditionsEmbed`, `ScoreBadge`, `Disclaimer`, `AffiliateLink`, `AdSlot`, `NewsletterForm`) hold the
cross-page conventions. The growth/ads components are scaffolding; the current privacy posture keeps
them inert until consent, disclosure, and a kill-switch are explicitly handled.

The marketing e2e suite checks unique metadata, canonical URLs, JSON-LD, sitemap/robots, internal
links, real-data content assertions, and absence of third-party references.

## 9. Atlas and geometry pipeline

The atlas is an important subsystem because its generated geometry is large, provenance-sensitive,
and independent from current gauge/stocking readings.

### Shipped atlas assets

`apps/web/public/atlas` contains:

- `rivers.geojson`, `lakes.geojson`, and road layers at major/mid/minor detail;
- Tennessee and surrounding-state context, boundary, county, and place data;
- `provenance.json` and road manifests;
- contour GeoJSON bands;
- nested hillshade WebP tiles under `topo/hillshade`.

The map also consumes generated `riverIndex.json`, `streams-geo.json`, `flowOrientation.json`, and
the content catalog to join geometry to user-facing water records.

### Build and QA scripts

The atlas scripts under `apps/web/scripts` are grouped by purpose:

- source fetch: `fetch-atlas-sources`, NHD, TIGER, Census, roads, DEM/topography;
- assembly: `build-atlas`, `merge-rivers`, `build-lakes`, `build-roads`, `build-atlas-context`;
- topology/continuity: `audit-river-continuity`, `close-residual-gaps`, flow-orientation scripts;
- targeted repairs: the `fix-*`, `west-middle-*`, and `east-*` scripts;
- validation/rendering: `validate-atlas`, `validate-roads`, `validate-topo`, render/QA scripts;
- integration: `integrate-verified-atlas`, `regenerate-river-index`.

The documented rules are conservative: preserve real source parts, avoid fabricated geometry,
reject out-of-state NHD parts, use explicit reach gates for tailwaters/pools, and document residual
gaps instead of quietly welding arbitrary lines. The map’s internal `?qa=1` mode audits the shipped
geometry client-side and lets a reviewer click from a defect row to the affected water.

Read [`docs/atlas-sources.md`](atlas-sources.md), [`docs/GEO-AUDIT.md`](GEO-AUDIT.md), and the
audits under [`docs/audits`](audits) before changing geometry or source-selection heuristics.

## 10. Testing and CI

### Package-level tests

Vitest covers:

- contracts: schemas, endpoint map, hatch matching, scoring, freshness, water evidence;
- API: migrations, health, seed, USGS/stocking parsing, retry/dry-run, evidence providers,
  snapshot assembly, portal routes, and conditions bridging;
- web: map selectors/camera/labels, atlas integration/availability, conditions, stocking, hatch,
  logbook, units, presentation, fieldwork, and components;
- admin: token/contracts, drafts, and portal interactions;
- content: pack/content validation helpers.

`packages/contracts` runs Vitest with coverage and the repository’s enforced coverage floor. The root
`pnpm test` intentionally does not run Playwright because the e2e package has no `test` script.

### Canonical Playwright projects

[`e2e/playwright.config.ts`](../e2e/playwright.config.ts) starts its own servers and runs with one
worker for deterministic service-worker/MapLibre behavior:

| Project | Port | Coverage |
|---|---:|---|
| `marketing` | 4321 | SEO, metadata, JSON-LD, internal links, third-party-request hygiene |
| `web` | 4173 | PWA shell, privacy, manifest, offline cold-start, conditions fixtures |
| `admin-portal` | 4174 | Real token login, composer publish, public attributed report feed |
| `fieldwork` | 4173 | Map UI, layers, conditions states, touch/pointer, themes, responsive behavior |
| e2e-only API | 8791 | Temporary seeded DB for portal/API tests |

`global-setup.mjs` builds the deterministic fixture web flavor and admin build. The API server script
creates a temporary database and seed/snapshot environment, so the portal e2e flow does not touch the

### GitHub Actions

`ci.yml` runs on Windows and gates install, lint, content validation, package tests, and build.

`qa.yml` runs the Playwright suite and Lighthouse. Marketing has SEO >=95 and accessibility >=90

### Deploy sequence

[`infra/deploy.sh`](../infra/deploy.sh) is the normal deployment script:

1. `git pull --ff-only`;
2. frozen-lockfile install;
3. build all packages;
4. validate content;
5. seed/update the SQLite catalog;
6. ingest live gauges, retaining last-known data if ingestion fails;
7. regenerate snapshots;
8. prerender web SEO routes when snapshots exist;
9. rebuild marketing from real snapshots when available;
10. reload/start PM2;
11. verify health, streams, conditions, and content endpoints;
12. reject the deployment if `/healthz` says the conditions feed is unhealthy.

The script sources a gitignored `.env` before building so the optional Cloudflare Web Analytics token
can be injected at build time. The token is not part of normal dev, fixture, CI, or privacy-audit
builds.

The operational details, backup/recovery steps, and the snapshot-sync fallback are in
[`infra/RUNBOOK.md`](../infra/RUNBOOK.md). The snapshot-sync fallback only replaces generated
`apps/web/public/v1` and `apps/web/public/content`; it never touches the API database or portal
writes.

## 12. Privacy and security boundaries

The intended privacy model is visible in code and tests:

- no visitor account or password flow;
- no browser geolocation API use in the read path;
- no coordinates in outbound requests;
- no third-party requests from normal web routes;
- no visitor logbook/settings data sent to the API;
- API logs redact authorization/cookie/network identity fields;
- shop tokens are bearer credentials with expiry and HMAC verification;
- portal drafts are browser-local and only become server data on explicit publish;
- portal CORS is restricted to configured portal origins;
- public shop reports are attributed and read-only after publication;
- analytics is build-time opt-in and documented as cookie-free aggregate measurement.

The tests in `e2e/web/privacy.spec.ts` and the route sweep in
`e2e/helpers/first-party.ts` are the most direct regression checks for the privacy promises.

## 13. How to make common changes

### Add or correct a water

1. Add/update the YAML in `packages/content/streams/{state}` with a stable ID, state, region,
   waterbody type, gauge IDs, ideal flow, and official sources.
2. Run `pnpm validate:content` and fix cross-reference/gauge warnings or errors.
3. If it needs geometry, follow the atlas source/fetch/assembly scripts and update the geometry
   provenance docs; do not hand-edit generated GeoJSON as the final source of truth.
4. Regenerate the river index/fixtures as required by the atlas workflow.
5. Build content, seed API, build snapshots, and run map/atlas tests.

### Add a bug, fly, or hatch entry

1. Author the YAML under `packages/content/bugs`, `patterns`, or `hatch`.
2. Ensure IDs and references match existing taxa/patterns/regions.
3. Provide required attribution/illustration information.
4. Run `pnpm validate:content` and `pnpm --filter @trout/content build`.
5. Regenerate snapshots if testing through the PWA/marketing/API path.

### Change a public payload shape

Start in `packages/contracts`, not in a single app. Decide whether the change is additive. Update
schemas, consumers, fixtures, unit tests, and relevant ADR/assumption notes. Contract comments and
the version/tag discipline are deliberate: a local shape change can break the web, API, marketing,
admin, and e2e environments at once.

### Change conditions scoring

Change [`scoreConditions.ts`](../packages/contracts/src/scoreConditions.ts), then update its focused
contract tests and the UI tests for score bands/reasons/unassessed states. Keep freshness separate
from scoring: scoring is a pure assessment of supplied readings, while staleness is decided by feed
timestamps and the client’s cached/live state.

### Change offline behavior

Inspect all of these together:

- `apps/web/src/lib/snapshots.ts` for fetch/cache/fallback truthfulness;
- `apps/web/src/lib/db.ts` for persistence boundaries;
- `apps/web/src/lib/useSnapshotQuery.ts` for query behavior;
- `apps/web/vite.shared.ts` for Workbox routes and precache policy;
- `apps/api/src/app.ts` and `infra/static-server.mjs` for server cache headers/fallback behavior;
- `e2e/web/offline-cold-start.spec.ts` for the real browser flow.

An offline fix is incomplete if it only changes one of those layers.

### Add a shop report field

Trace the field through the entire write path:

```text
admin composer/input schema
  → portal route validation
  → migration/database column
  → snapshot builder mapping
  → ShopReport contract
  → public report rendering and e2e assertions
```

The photo URL history is the model: it required an additive contract decision and an ADR because
portal input, stored reports, and public snapshots do not automatically have identical shapes.

## 14. Known gotchas and current-state notes

1. **The root README is partly historical.** Use the current source tree, `PROGRESS.md`, ADRs, and
   this guide for the implementation state. In particular, the map/atlas/evidence work is newer than
   the Phase-0 status paragraph.
2. **Launch state is Tennessee in code.** `V1_STATES`, content, atlas assets, and marketing fixtures
   are TN-centered even where older planning text mentions TX/OK/AR.
3. **Generated snapshots are not source files.** They live under `apps/web/public` and are produced
   by seed/ingest/snapshot commands and deploy/cron. Do not “fix” live conditions by editing JSON by
   hand.
4. **`/v1/streams` is special.** It is served from `streams.json` by a live Fastify handler so state
   filtering works. The remaining snapshot endpoints are static mounts.
5. **No-store headers are intentional.** Workbox and Dexie are the offline layers; browser HTTP
   caching must not make an old snapshot look live.
6. **Fixture builds are real hosting simulations.** The Playwright web project uses the fixture build
   so it tests extensionless `/v1/*` URLs, service-worker registration, and static fallback behavior.
7. **The portal is not the PWA.** It has its own origin/build and local token/draft state. Its only
   dynamic server operation is explicit report publication.
8. **`MARKETING_DATA_DIR` changes the data source.** Without it, marketing uses deterministic fixtures;
   deploy sets it after snapshot generation so SEO pages reflect the published catalog/data.
9. **The API path is cwd-sensitive only when configuration overrides are wrong.** `pipeline.ts` now
   anchors defaults at the module/repository root because PM2 and pnpm invoke jobs from different
   working directories.
10. **Atlas geometry has its own provenance contract.** Water catalog copy should stay angler-facing;
    source IDs, topology evidence, and repair rationale belong in atlas provenance/audit documents.
11. **The current worktree is not clean.** At inspection time, `.env.example`,
    `apps/web/vite.shared.ts`, and `infra/deploy.sh` were modified, and `plugins/` was untracked.
    Those changes were preserved; this guide does not infer ownership or overwrite them.
